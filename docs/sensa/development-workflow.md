# Sensa 开发工作约定

> 状态：当前采用，可根据实际开发情况调整
> 确认日期：2026-09-05
> 适用范围：Sensa 正式 Web、浏览器插件、API、共享模块及后续 Flutter 的用例开发
> 版本：工作方式 v2；不属于领域模型或不可调整的架构决定

## 当前 owner 修订（2026-09-07）

Owner 已明确要求后续不再使用 worker 模式，由主代理直接设计、实现、审查和验证；
允许浏览器测试。每条用例线完成并通过检查后，直接创建 Git checkpoint 提交；

## 1. 基本方式与文档职责

全局结构自上而下规划，具体工作按端到端用户用例纵向交付。每条用例先由 owner 与负责该轮
的 supervisor 或 worker 确认前端体验，再据此细化消费契约、持久化和同步，进入正式实现。

模块是架构上的责任边界，纵向用例是默认的开发和验收单位。底层函数与组件可以先实现，但
应在本条用例内尽早组合并贯通，不等整个系统的所有底层模块完成后才集成。

- [领域文档索引](README.md)中的七份领域文档裁决身份、所有权和不变量。
- [PRD](product-requirements-v1.md) 与 [首轮产品基线](first-round-product-baseline.md)
  管理产品职责、范围与状态；[current-stage.md](current-stage.md) 管理当前阶段。
- [生产化路线图](production-migration-plan.md) 管理做什么、依赖顺序和里程碑验收。
- 本文管理怎样设计、确认、委派、实现、审查和调整工作方式，不另列一份生产任务清单。
- [web-next 前端先行规范](../../apps/web-next/FRONTEND_FIRST_WORKFLOW.md)作为原型与
  消费需求发现的补充；原型移交生产后，前端驱动用例确认的原则继续适用。

本约定记录当前的协作选择，不声称全局蓝图、具体用例 UI 或生产合同已经完成。

## 2. 分工与责任

| 角色 | 负责什么 | 可以自主决定什么 |
| --- | --- | --- |
| Owner | 产品取舍，与指定 supervisor/worker 确认界面、功能、状态与交互；验收体验 | 功能范围、用户流程及产品优先级的调整 |
| Supervisor／蓝图负责人 | 整体结构、模块边界、数据所有权、共享类型与契约、任务拆分、集成审查和最终验证 | 不改变已确认体验和领域规则的结构细化、依赖安排与实施协调 |
| Implementation worker | 在约定范围内实现整条用例或明确的子任务，验证并交付；可被指定与 owner 共创前端方案 | 模块内部的算法、辅助函数、局部组织及其他不改变公开契约的实现细节 |

Supervisor 对设计一致性和交付质量负责，不以提前指定所有内部函数来替代审查。Worker 发现
合同缺口或设计矛盾时反馈具体场景与候选方案；跨模块设计由 supervisor 统筹修订，不能为了
局部实现方便自行改变领域归属或用户已经确认的行为。

实施 worker 的选择、允许的替代执行方式、小型 supervisor 修复例外和文件所有权仍遵守仓库
工作约定。本文不因为采用“蓝图负责人”分工而要求每个小改动单独委派。

## 3. 蓝图的两层精度

### 全局结构蓝图

可以在具体页面确认前确定：系统的模块划分与职责、目标目录结构、模块间依赖方向、领域
身份、数据所有权、跨端共用边界和全局不变量。形成可查阅的模块图、目录树与责任说明，
覆盖系统主要部分，并标明已确定、暂定及后续再细化的内容。

这不是冻结整个项目的最终文件和函数清单。逻辑数据模型可以先确定身份和关系；面向具体
页面的 Projection、HTTP 形状、表结构、索引与事务实现，应随用例需求和验证结果细化。

### 本轮用例施工蓝图

前端体验确认后，将本轮用例落实为 worker 能直接实现和验收的产物：

| 产物 | 所需精度 |
| --- | --- |
| 目录、文件与模块清单 | 列出本轮实际涉及的文件、职责、所有权、依赖与允许的调用路径 |
| 共享类型与接口 | 固定用例输入/输出、Query/Command、错误、版本、operation identity 和并发语义 |
| 数据与行为规则 | 明确事实归属、状态转移、原子提交、幂等、恢复以及派生结果的权威边界 |
| 前端消费与状态映射 | 将已确认界面状态和操作映射到合同；指出本机状态、乐观反馈与服务端确认结果 |
| 必要的验证依据 | 给出可重现的输入/结果、关键边界场景和端到端验收路径 |

蓝图以目录树、模块/依赖图、类型和接口声明、状态表及必要的可执行契约检查共同表达，文字
解释设计理由。只写“实现某模块”不能代替这些边界；同时不为凑齐蓝图而创建大量无消费者的
空文件、占位生产实现或镜像实现细节的测试。

精度优先集中在模块接口与关键规则。调度幂等、语义接纳等高风险行为必要时可以约束到函数
签名和行为，普通辅助函数交给 worker。蓝图不足以指导当前任务时先补齐相关部分，不把整个
未来系统的细节补完作为本轮开工条件。

## 4. 每条用例的工作循环

### 4.1 选定一个用户结果

明确所属里程碑、入口、终点、用户、必要前提与本轮不包含项。例如在插件阶段：选取网页
文字 → 保存待处理 → 服务端接纳 → Web 收件箱显示 → 刷新后仍存在。该切片可以先完成，
后续再增加原位解析、确认和加入学习，所有切片仍服务于同一领域主旅程。

### 4.2 与 owner 确认前端体验

Owner 与本轮指定的 supervisor 或 worker 一起确认：

- 布局、信息层级、文案和主要操作；
- 用户能做什么，操作成功后得到什么，怎样返回或继续；
- 本用例相关的 loading、empty、pending、preparing、blocked、offline、conflict、失败与重试；
- 离开、刷新、取消、重复操作及恢复行为。

按用例需要使用线框、界面稿、状态表或可操作原型。复杂交互应能走查，简单修改可直接在
现有界面上确认；不要求每个用例重建一套原型。原型代码和确定性场景允许用于确认体验，
不能据此声称生产持久化或服务端行为已经完成。

记录 owner 确认所对应的产物/版本、用例范围、日期和仍待处理项。既有明确确认在同一范围
内继续有效，不因换 worker、分成多个提交或进入后端实现就要求重复确认。

### 4.3 从前端需求细化合同与蓝图

Supervisor 将已确认的用户意图和状态转成消费合同，并设计必要的持久化与同步方案。既有
后端、旧表或已写类型是复用输入，不主导界面功能和工作流；不匹配时先判断应调整哪一层。

前端也不能改变领域事实的所有权。若体验要求与领域规则、可用资源或真实技术能力冲突，
supervisor 说明具体影响并给出可讨论方案；涉及用户可见行为的调整回到 owner 确认。
Worker 不自行删除功能、隐藏失败状态或以虚假成功补齐缺失能力。

正式用例实现的开工条件是：相关前端体验已经确认，当前消费合同足以指导实现，领域与关键
边界没有未裁决冲突。全局结构设计、必要的技术探查可以先行，但不能被当作体验已确认。

### 4.4 Worker 纵向实现

按施工蓝图完成该用例涉及的正式前端、API、业务规则、数据库、同步和资源适配。单个 worker
可以跨多个模块工作，同时遵守各模块的边界与文件所有权。自下而上的函数/组件实现发生在
本条切片内部，并尽早通过真实数据接通端到端路径。

默认一个主要实现 writer。只有任务依赖、接口和文件所有权明确且互不冲突时，才引入有限
并行；不以已画出模块图为理由一次启动大量独立 worker。共享文件由 supervisor 协调串行
修改，不能由多个 worker 各自重定义。必要时可委派模块/函数子任务，但最终按用例集成验收。

### 4.5 审查、实际验收并反馈

Supervisor 审查边界、契约、数据正确性、可维护性及实际 diff，运行仓库要求和该用例相关的
验证，并从前端检查真实持久化、错误与恢复行为。Worker 的局部检查通过不等于用例已贯通。

交付附上前端产物、确认依据、合同/代码、测试环境与结果、已知限制。Owner 可以检查最终
体验是否符合确认内容；实现偏差应修复，确需改变体验时重新确认受影响部分。技术集成通过
和用户体验确认分别记录，不用其中一项冒充另一项。

将实际实现暴露的问题反馈到蓝图与当前任务，再继续下一条用例。验收范围、根级检查、
相关集成/浏览器 smoke、付费调用与部署边界遵守仓库和路线图要求；不扩大为全仓单元测试工程。

## 5. 一份实施任务的最小内容

任务单可以简短，但必须能回答：

1. 要完成哪个里程碑中的哪个用户结果，验收入口和终点是什么？
2. Owner 已确认的界面/状态产物在哪里，哪些内容仍未确认？
3. 本轮目录与模块蓝图、类型/接口、关键数据和行为合同在哪里？
4. 仓库路径、worker 文件所有权、允许的依赖、适用指令与不包含项是什么？
5. 需要哪些前置能力，怎样验证成功、失败、中断和恢复，怎样交付证据？

文件可链接既有产物，无需每次复制全部文档。纯内部维护或不改变既有体验的修复，引用已经
确认的用例及契约即可；没有用户界面的基础设施工作不为流程补造界面，但要有具体消费者、
运行结果和适当验证。小型任务可合并步骤，不要求新增完整文档包。

## 6. 根据实际开发调整

本约定是当前默认方式，不是永久冻结的流程。用例太大、交接反复、接口返工、验证不足、
等待过多或实现成本不合理时，都可以调整切片粒度、蓝图精度、协作方式和验证安排。

| 调整类型 | 处理方式 |
| --- | --- |
| 模块内部实现 | Worker 在既有边界内直接处理；由 supervisor 正常审查，不另设 owner 确认 |
| 不影响体验和领域规则的结构细化 | Supervisor 协调、更新蓝图和受影响任务；已有消费者存在时验证兼容性 |
| 改变已确认界面、功能或用户操作结果 | 带回具体差异、原因和候选方案，与 owner 确认受影响部分后再实现 |
| 改变领域身份、所有权、不变量或当前交付范围 | 按对应领域/产品权威讨论裁决，同步有关文档与合同，不由内部重构暗中实现 |
| 改变协作流程本身 | 根据实际问题提出调整；日常粒度/人员安排由 supervisor 在既有授权内处理，影响 owner 参与方式或确认原则时共同讨论 |

对会影响后续工作的调整，简要记录“遇到的问题、调整内容、适用范围和验证结果”，优先放在
对应任务/交付记录中。稳定成为新默认后再更新本文；特定用例的例外不自动推广到全项目。
不为每个辅助函数或普通重构创建决策文档，也不为维护流程形式而重复请求已经获得的确认。
