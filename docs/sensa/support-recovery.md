# Sensa Web 支持与恢复手册

本文用于已发布 Web、浏览器扩展、账号同步和在线服务的用户支持与事故恢复。它不承诺数据库供应商尚未配置或尚未演练的备份能力；代码、迁移、发布 workflow 和实际生产配置仍是操作事实来源。

## 首要原则

1. 在确认可恢复副本前，不要求用户清除网站数据、重装浏览器、删除账号或覆盖云端 checkpoint。
2. 能打开本机资料库时，先从“账号与设置 → 设备与数据 → 加密备份”导出，并由用户保管密码。支持人员不索取备份密码、模型密钥、登录验证码或 token。
3. 诊断文件只用于定位版本、浏览器能力、存储与同步状态。用户应先查看文件再发送；若需要学习内容或截图，必须另行说明范围和原因。
4. 云同步是当前收敛 checkpoint，不是历史备份。浏览器 persistent storage 只能降低自动驱逐风险，不能防止用户主动清除网站数据。
5. 所有数据库修复和删除都按账号精确定位、先只读核对、再由 owner 授权。不得用全库清理代替单账号恢复。

## 支持受理

请用户提供：问题发生时间和时区、操作步骤、浏览器与版本、是否仍能打开本机资料、是否有加密备份、产品显示的诊断/请求 ID，以及产品内下载的脱敏诊断文件。不要要求用户粘贴邮箱验证码、完整 URL、私密学习内容、模型输入输出或浏览器存储文件。

先按以下类别分流：

| 状态 | 先做什么 | 不要做什么 |
| --- | --- | --- |
| 提示其他标签页版本不同 | 关闭同一站点的其他标签页，保留当前页面，确认没有等待中的编辑后重新加载 | 不清除网站数据，不删除 OPFS 文件 |
| 更新已准备好 | 完成当前操作后使用产品内“立即更新”，等待页面自动重载 | 不同时在多个旧标签页继续写入 |
| 本机资料库不可用/空间不足 | 停止新增，记录诊断；若仍能进入数据页先导出备份，再检查浏览器能力和空间 | 不把内存 fallback 或空库当成恢复成功 |
| 提示“恢复本机资料” | 保留当前浏览器资料，先重新打开；有已验证加密备份时在恢复入口检查并明确恢复，账号备份先登录原账号 | 不清除浏览器数据，不把缺失身份解释为首次使用，不覆盖恢复期间新增的资料 |
| 无法恢复且用户决定重新开始 | 在恢复入口明确确认另建本机库；退出当前登录，保留旧目录及库选择引用；新库失败可重新打开 | 不把新空库视为恢复成功，不清空旧文件；浏览器主动清除网站数据仍会同时丢失保留文件 |
| 同步 pending/offline/failed | 保留本机页面与数据，恢复网络后手动重试；terminal 状态转支持 | 不退出账号，不清理本机副本 |
| 同步 conflict | 先导出备份，再在冲突界面明确选择本机或云端版本；应用选择前系统会重新检查云端 revision | 不依据时间戳替用户选择，不直接改数据库 head |
| 只有云端副本 | 在空的受支持浏览器中登录，等待恢复完成，核对资料后立即导出加密备份 | 未核对前不要从另一设备上传空库 |
| 只有加密备份 | 使用空浏览器资料恢复，核对库 identity、个人内容、媒体和学习事实，再决定是否连接账号同步 | 不覆盖仍可能包含更新内容的现有库 |
| 账号删除 | 核对确认挑战、请求 ID 和删除结果；提醒用户其他设备的离线副本需分别清除 | 不把 Auth 用户消失当成全部业务数据已删除 |

## 操作恢复顺序

1. 保存用户可恢复副本与脱敏诊断。
2. 用发布 SHA 确认 Web、Service Worker、API 和数据库迁移所处版本；旧页面不得对未知新 schema 写入。
3. 使用 CI 中同类无成本测试复现。涉及 OPFS 时运行 `npm run test:browser`；涉及 API/Edge 时运行 `npm run test:edge`；涉及账号数据时只在隔离测试库运行 `npm run test:db`。
4. 若为发布回归，优先停止继续推广并部署已验证的修复版本。数据库迁移只前进，不回滚或手工删除列；应用回退前必须证明旧应用理解当前 schema。
5. 若需要数据库恢复，先验证备份产品中确实存在目标恢复点、账号范围、加密配置和恢复演练记录。在隔离环境恢复并核对后，才可制定生产操作；没有这些证据时如实报告“尚无已验证恢复点”。
6. 修复后核对本机记录、云端 revision、同步状态、媒体可读性、学习历史和账号隔离。用户确认前保留原副本。

## 首批邀请用户的认证核验

认证由 Supabase Auth 负责，认证邮件通过自定义 SMTP 投递；业务在线资格由
`sensa_consumer.invitations` 独立控制。获得邮件／Auth 会话不等于已获得业务资格，不能通过切换为开放注册、
管理员生成验证链接或绕过公开登录来认领验收成功。

首批邀请先核对真实 Auth subject、所属项目和 owner 授权，再按精确 issuer／subject 登记；不要按邮箱猜测身份、
批量开放或重新启用已有撤销记录。当前没有用户侧邀请管理页面；生产登记属于单独授权的运维动作，
不能把本机测试库的 `registered` 准入结果当成生产邀请结果。

固定发布版本后，使用隔离的受支持浏览器通过公开页面完成发送、真实收件、同一浏览器回调、API 准入、
重开恢复和实际开始学习。邮箱链接、验证码与私有浏览器状态不进入报告或 Git。供应商 `delivered` 只证明
接收服务器接收，还需用户确认收件箱／垃圾邮件位置。链接失效、429 和未邀请状态不得显示成功；退出
后核对已有本机资料仍可用。自动化使用受控 Auth 与隔离 PostgreSQL，不在常规 CI 中发送真实邮件。

## 发布与事故演练

每个真实用户发布候选至少记录以下结果：固定 SHA 的 CI、Chromium/OPFS 套件、部署后 public smoke、受控告警演练，以及支持入口可达。真实邮箱登录、邀请资格、Auth redirect/token refresh 和支持邮箱收件必须使用外部邮箱人工验收，不能由本地假 Auth 或单元测试代替。

告警演练必须产生维护者实际收到的 GitHub incident，记录发现、分类、恢复和关闭时间；演练内容不得包含用户数据。任何未执行项保留为发布阻断项，不写成“已通过”。

发布 workflow 的成功状态只证明该运行实际执行的边界，不代替上面的邮件、告警或恢复演练。
未核验的准备项在 issue tracking 中明确保留；已有生产发布不是它们已经通过的证据。下载的系统 manifest
和原始验收报告按工程说明中的证据归档方法保存，原始报告保留被测版本和实际观察，不追加推测的成功状态。

## 关闭支持事件

关闭前记录稳定错误类别、受影响发布 SHA、影响范围、恢复动作、用户核对结果和需要补充的自动化测试。不要把邮箱、内容、token、完整 URL、堆栈或数据库行复制进公开 issue。代码修复、测试和 workflow 是长期证据；临时调查日志按承载系统的保留策略处理。
